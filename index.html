Why Technical Documentation is Produced in Markdown Format

The technical documentation you are about to evaluate is produced in Markdown (.md) rather than plain text, HTML, or PDF. This is not an arbitrary choice — it follows directly from how computational notebooks are structured and how the field empirically defines "documentation."

Notebooks such as Jupyter interleave executable code with rendered narrative text, and that narrative text is written as Markdown. Siddik (2025) confirms the Markdown cell as a defined notebook cell type, and notes that Jupyter's own conversion pipeline (nbconvert) treats Markdown as the source format from which HTML, LaTeX, and PDF are generated — every other export representation is derived from Markdown, not the reverse.

The empirical literature on notebook documentation quality is itself built around the Markdown cell. Siddik (2025) and Liu et al. (2021) both define "documentation" as Markdown-cell content, and Rule, Tabard, & Hollan (2018), studying over one million public notebooks, found that 99.8% of all cells are either Markdown or code. Most directly relevant here, Wang et al.'s CHI 2021 study of 80 highly-voted Kaggle notebooks — the same selection rationale used for this thesis's dataset — found that observed documentation practice falls entirely into nine Markdown-cell categories: Process, Headline, Result, Education, Reason, Todo, Reference, Meta-Information, and Summary.

Producing the framework's technical documentation output in Markdown, therefore:
Structural fidelity Preserves structural fidelity with the notebook artifact being documented.
Empirical alignment Aligns the output with the field's own empirical standard for what constitutes documentation, allowing direct comparison against the reference literature.
Format flexibility Does not sacrifice presentation flexibility — Markdown is the canonical source from which polished HTML or PDF versions can be mechanically and losslessly generated later, e.g. via pandoc or nbconvert-style tooling.

Part B: Ground-Truth Documentation Structure

The ground-truth documentation was authored as a standalone Markdown document per notebook — not as inline annotations — so it can be directly compared against the framework's own output, which takes the same standalone form. This also reflects a real gap in practice: Wang et al. (2021) found that most inline Markdown annotation explains local code rather than whole-notebook properties such as cross-cell dependencies or full-lifecycle synthesis, a gap linked elsewhere to reproducibility failures (Pimentel et al., 2019; Kashiwa et al., 2026).

Accordingly, each ground-truth document was authored using a fixed, six-section structure, applied identically across all 20 notebooks:
  1. (1) Notebook Overview: the problem, dataset, and scope of lifecycle coverage.
  2. (2) Environment and Dependencies: libraries, versions, and setup.
  3. (3) Per-Stage Documentation: a subsection for each machine learning lifecycle stage actually present in the notebook, including interpretation of any charts, tables, or metrics produced at that stage.
  4. (4) Cross-Cell Dependency Analysis: data-driven, result-driven, and model-evolution dependencies connecting cells that are not adjacent to one another.
  5. (5) Model Performance Summary: evaluation metrics and comparative results consolidated in one place.
  6. (6) Conclusions and Recommendations: a synthesis of the notebook's overall outcome. This structure was held fixed across all 20 notebooks so that any variation in the resulting documents reflects genuine variation in the underlying notebooks rather than inconsistency in documentation methodology.
