Why Technical Documentation is Produced in Markdown Format

Before reviewing the documentation samples, please read the following short explanation of a key methodological choice in this study: why the output format of the technical documentation you are about to evaluate is Markdown (.md), rather than plain text, HTML, or PDF. This is not an arbitrary implementation choice; it is grounded in the empirical literature on computational notebook documentation, as summarized below.

Computational notebooks (e.g., Jupyter) are not plain scripts with comments; they are built, from their conceptual origin in literate programming, as an interleaving of executable code and rendered narrative text, and that narrative text is written and rendered as Markdown. Saeed Siddik's systematic treatment of notebook structure confirms that the Markdown cell is one of the notebook format's defined cell types, and that Jupyter's own official conversion pipeline (nbconvert) treats Markdown as the source representation from which HTML, LaTeX, and PDF outputs are generated (Siddik, 2025). In other words, Markdown is not merely a documentation format notebooks happen to support; it is the specific format from which every other export representation is derived.

Independent of the notebook format's internal design, the empirical research literature on notebook documentation quality is itself built around the Markdown cell as its unit of analysis. Two independent research efforts converge on defining "documentation" as Markdown-cell content (Siddik, 2025; Liu et al., 2021). Rule, Tabard, and Hollan's large-scale study of over one million publicly shared notebooks found that 99.8% of all notebook cells are either Markdown or code, establishing Markdown-cell content as the field's own measure of what constitutes a documented notebook (Rule et al., 2018). Most directly relevant to this study, Wang et al.'s CHI 2021 study, which used highly-voted Kaggle notebooks as a proxy for well-documented notebooks, the same rationale this thesis uses for its own dataset, analyzed 80 such notebooks and found that the entirety of observed documentation practice falls into nine Markdown-cell content categories (Process, Headline, Result, Education, Reason, Todo, Reference, Meta-Information, Summary) (Wang et al., 2021).

Producing the framework's technical documentation output in Markdown, therefore:
  • (1) Preserves structural fidelity with the notebook artifact being documented.
  • (2) Aligns the output with the field's own empirical standard for what constitutes documentation, allowing direct comparison against the reference literature.
  • (3) Does not sacrifice presentation flexibility, because Markdown is the canonical source format from which polished HTML or PDF versions can be mechanically and losslessly generated at any later point, for example via pandoc or nbconvert-style tooling.

Dataset Selection Criteria and Ground-Truth Documentation Structure

This page explains two further methodological choices underlying the materials you are about to review: how the 20 notebooks in the evaluation dataset were selected, and why the human-authored ground-truth documentation takes the specific structure it does.

Part A: Dataset Selection

The 20 notebooks used in this study were selected according to the criteria defined in the thesis proposal, from three independent sources: a public dataset of Kaggle notebooks with rich metadata (KGTorrent; Quaranta, Calefato, & Lanubile, 2021), notebooks independently curated directly from the Kaggle platform, and notebooks independently curated from GitHub. Selection was governed by four criteria, applied jointly: (1) a Kaggle gold/silver medal or a comparable community-engagement threshold, more than 10 votes on Kaggle, or more than 10 stars on the hosting GitHub repository; (2) diversity of the underlying dataset and domain; (3) diversity of complexity and coverage of different stages of the machine learning lifecycle (problem definition, data collection, preprocessing, exploratory data analysis, feature engineering, model selection and training, and model validation); and (4) the presence of rich multimodal outputs, such as charts, tables, and other visual results, as an integral part of the notebook. These criteria were applied deliberately to produce a dataset spanning a wide range of complexity, from short, single-stage notebooks to long, full-lifecycle, multi-model pipelines.

Part B: Ground-Truth Documentation Structure

The ground-truth documentation you are about to review was authored as a standalone Markdown document per notebook, rather than as annotations inserted into the notebooks themselves. This was a deliberate methodological choice, made necessary by the evaluation design of this thesis: since the proposed framework generates a single, standalone Markdown file per notebook, the human-authored reference document must take the same form for the two to be meaningfully compared side by side.

This choice is further grounded in a substantive distinction the literature draws between code documentation, locally-scoped explanations attached to a specific line or cell of code, and technical documentation in the fuller sense this thesis targets: a structured account of a notebook's purpose, process, reasoning, results, and interpretation, considered as a whole. Wang et al. (2021) found that the dominant, majority use of inline Markdown-cell annotation in real notebooks is local code explanation, while whole-notebook properties, connecting cells that are far apart, synthesizing results across the entire notebook, and covering the full machine learning lifecycle, are, by the same study's own framing, cases that go beyond what locally-scoped annotation typically captures. This gap is echoed throughout the applied literature: Liu et al. (2021) motivate their own documentation-generation model by observing that "one documentation in a markdown cell often corresponds to multiple code cells," and multiple studies link the absence of whole-notebook documentation directly to measured reproducibility failures, for example, Pimentel et al. (2019) found that only 24% of a large sample of GitHub notebooks were fully executable and only 4% reproduced identical results on re-execution, while Kashiwa et al. (2026) found only 2 of 19 attempted notebooks accompanying peer-reviewed Nature publications were successfully reproducible.

Accordingly, each ground-truth document was authored using a fixed, six-section structure, applied identically across all 20 notebooks:
  1. (1) Notebook Overview: the problem, dataset, and scope of lifecycle coverage.
  2. (2) Environment and Dependencies: libraries, versions, and setup.
  3. (3) Per-Stage Documentation: a subsection for each machine learning lifecycle stage actually present in the notebook, including interpretation of any charts, tables, or metrics produced at that stage.
  4. (4) Cross-Cell Dependency Analysis: data-driven, result-driven, and model-evolution dependencies connecting cells that are not adjacent to one another.
  5. (5) Model Performance Summary: evaluation metrics and comparative results consolidated in one place.
  6. (6) Conclusions and Recommendations: a synthesis of the notebook's overall outcome. This structure was held fixed across all 20 notebooks so that any variation in the resulting documents reflects genuine variation in the underlying notebooks rather than inconsistency in documentation methodology.
